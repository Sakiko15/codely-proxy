## 三、缺陷清单——P1（7 项，全部建议修复）

### P1-1【M5】SaveAccount(activate) 提交顺序与 ActivateAccount 相反 → 失败即持久化不一致
`internal/account/registry.go:421-433`（对照正确序 `:478-488`）。先 `idx.Current=slug`+saveIndex 落盘（:422-424），**后**写 codely-creds.json（:429）。后者失败（磁盘满/权限）→ index 指向新账号而激活凭据仍是旧账号；无自愈路径（legacy 导入仅在 index 为空时触发）。后果：/healthz、GetCurrentMeta、免调度 Pick 全按新账号报告，实际流量走旧凭据。
**修复**：镜像 ActivateAccount 顺序——SaveCreds 成功后再提交 current+saveIndex；或失败时回滚 idx.Current 并重写 index。

### P1-2【M5】ActivateAccount 预取回写无"仍是当前账号"守卫 → 切换窗口静默串号
`registry.go:494-501`。解锁后网络预取（最长 30s+），窗口内他人 ActivateAccount(B) 后，:500 `_ = updated.SaveCreds()` 无条件用 A 的轮换凭据覆盖 codely-creds.json → current=B、激活凭据=A，全局流量以 A 身份发出且永不 401 自愈（A 的 token 有效）。
**修复**：回写前持 r.mu 复查 `loadIndex().Current == slug`。与 P1-5/P1-6 同根，一个守卫 helper 可三处覆盖。

### P1-3【M6】persistCreds 轮换凭据落盘失败被三重静默吞 → 账号永久刷废且零日志
`internal/balancer/account_state.go:300-303`（`_, _, _ = s.registry.SaveAccount(...)`），调用点 :257/:265/:330。上游 refresh 是轮换式（:286-288 注释自证）——落盘失败即新 refresh_token 丢失，文件留已作废旧 token，下次刷新必 invalid_grant，账号只能重新设备码登录。全程无日志。
**修复**：persistCreds 返回 error 并记日志；失败重试一次。

### P1-4【M6】双凭据库轮换互踩：balancer 只写 a.json，全局链只写 codely-creds.json
`account_state.go:300-303` vs `oauth/creds.go:163-202`。激活账号经池路径轮换后 codely-creds.json 持已作废 refresh_token → 全局 access_token 过期时刷新必败 → /quota 面板报错；反方向：全局轮换后 a.json 陈旧，"重新激活"会反向污染（registry.go:470 复制回写）。佐证既定意图：激活预取路径 `registry.go:499-500` **确实做了双写**，balancer 的 persistCreds 漏了 `slug==当前账号` 分支。
**修复**：persistCreds 在 slug 为当前账号时追加 SaveCreds；全局 RefreshAccessToken 成功后对称回写 accounts/<current>.json；或收敛单一事实源。

### P1-5【M10】quota fetchFresh 全局回写无守卫（P1-2 同根，窗口最宽）
`internal/quota/quota.go:238-243`。:181 取凭据到 :242 SaveCreds 之间串行 4 次控制面往返（usage/plan/换 key/key/info），秒级到数十秒窗口。:241 注释"由下次 401 自愈"**不成立**（写入的 access_token 有效，永不触发 401）。另有弱同族：`:249` 快照名牌取组装时 current，切换窗口内单次响应"旧账号数字+新账号名牌"（不跨请求持久）。
**修复**：与 P1-2 同一守卫；顺带修正注释与 :249 取同源账号摘要。

### P1-6【M4】RefreshAccessToken 全局回写同族窗口（P1-2 同根）
`oauth/creds.go:165→193`。LoadCreds 到 SaveCreds 之间一次刷新 RTT（≤30s）；singleflight 只防重复刷新不防切换。IsExpiring 60s 窗口内恰逢切换即触发。
**修复**：守卫失败则跳过写盘、仅把 token 交还本次调用（该路径无 per-slug 文件可写）。

### P1-7【M7】system 块数组（Claude Code 主流形态）击穿零拷贝 + 数字失真 + 空白块误删
`internal/sanitize/sanitize.go:57-74` + `:242-248` + `:279-282`。`sanitizeSystem` 块数组路径用 `[]map[string]any` 解码后**无条件** `json.Marshal`（:73）→ map 键重排 → `:244` bytes.Equal 恒不等 → changed=true → 每个请求付全量重组（零拷贝 :279-281 对主流量永不可达）；块内数字经 float64 往返失真（>2^53），`:282` 注释"值级字节保留"对 system 块失真；`:66-68` 纯空白 text 块即使无违禁词也被静默剔除。幂等性仍成立（第二次键序已同），故现有测试全绿但路径已死。
**修复**：块数组改 `[]json.RawMessage` 粗解 → 仅对 text 为 string 的块做"改写前后字节比较"，无任一块实际改写时整体原样返回；空白块剔除仅在实际清洗时执行。补"块数组零改动 → changed=false"与"块内大整数保真"两条对位测试。

## 四、缺陷清单——P2（38 项，按模块分组）

**M3/M8（协议层）**
1. ClientHeaders 定义位置与 GO_PORT §1/§18.1 矛盾（gateway vs 实际 oauth/apikey.go:128）——文档/可维护性
2. CodelySignature 每请求重算常量 k1（signature.go:65）——微性能，可选
3. sseguard content_block_stop index 解析失败时清空全部开放块（guard.go:129-132）——防御方向反了，恰复活"start 后无 stop 挂死"；index 解析不容忍冒号前空格与 eventType 正则不对称
4. 行缓冲无长度上限（guard.go:146/203）——畸形无换行上游可放大内存（真实 SSE 恒有换行）
5. UTF-8 BOM 不被 TrimSpace 剥离——实际影响≈0
6. AnthropicGuard.Finish 残留行缓冲分支无专属测试（TestAnthropicChunkBoundary 注释声称覆盖但实际未进入——注释误导）

**M9（转发编排）**
7. 末次尝试的 KindRetryKey 仍执行 RefreshAPIKey，结果被丢弃（handler.go:194+202-208）——多一次上游刷新+落盘
8. >64KB 错误体截断透传且 teamModelDeniedRE 可漏判 → 模型拒误分类为 RetryKey（forward.go:170/180；实践中概率极低）
9. copyHeaders 未滤 hop-by-hop 响应头（handler.go:331-340）——上游 Connection: close 会强制关下游连接（RFC 7230 §6.1）
10. 502 reason 字节截断可劈开 UTF-8 序列（handler.go:271-273）
11. 错误路径 body 未排空即 Close → keep-alive 连接不可复用，每次 4xx 多付握手（forward.go:170-181）

**M5（注册表/登录）**
12. complete() 双重激活冗余 + 失败文案失真（"已保存但激活失败"——实际 SaveAccount(activate=true) 已激活）（login_flow.go:394-403）
13. Slugify 放行 Windows 保留设备名（con/nul/com1-9/lpt1-9，registry.go:63）——Windows 登录报晦涩错误（与 M12-F6 同一发现）
14. poll 失败 message 可携带 auth_request_token（login_flow.go:172-182，url.Error 含完整 URL）
15. RemoveAccount 的 os.Remove 静默失败 → 半删除态无告警（registry.go:526-529）

**M6（负载均衡）**
16. 并发 UpdateConfig 落盘次序可与内存生效颠倒 → 磁盘回退旧配置（balancer.go:324-364）
17. preferred 钉住绕过 disabledSlugs（balancer.go:174-180，仅查 excluded）——与 GO_PORT §8.2/卡片措辞出入，二选一：补校验或明确钉住语义
18. KindRetryKey 路径不计 metrics（handler.go:198-209）——坏账号在面板上隐形
19. GetStatus 持 b.mu 做每账号文件 IO（status.go:51-67）——WebUI 轮询期间阻塞全部 Pick
20. FetchQuota 冷启动分支无 singleflight（account_state.go:309-363）——新账号首波并发重复打上游

**M4/M10（凭据/配额）**
21. Creds.UserID 裸 string 而非 FlexString（creds.go:52，schema §1 规定 FlexString；:45 注释自称 FlexString 语义但类型不符）——数字 user_id 的 legacy/手编文件整链"凭据不存在"
22. creds.go 私有 postJSON/getJSON 与 apikey.go 换 key 无 CLI UA、非 2xx 无 BodySnippet（creds.go:118,128,143、apikey.go:85,101,113；http.go:90 注释与实况不符）
23. quota 缓存指纹不含 slug + ClearCache 全仓零调用（registry.go:377-388、quota.go:189,271-277）——同 user+team 双 slug 15s 内互读快照
24. GetAccessToken 刷新后仅回填 AccessToken，调用方持过期 RefreshToken（creds.go:243-256）——同快照内 key 端点再 401 必败（下次 FetchSnapshot 自愈）
25. 跨组件同账号并发轮换无统一 singleflight（tokenRefreshFlight/refreshFlight/quotaFlight 互不感知）——last-writer-wins 可把败者 RT 落盘
26. 刷新响应缺 expires_in 时保留旧 ExpiryDate → 逐请求轮换循环（creds.go:189-192，防御性；上游现状恒发）

**M7/M11（清洗/安全）**
27. 登录限速实为 tumbling window 非滚动窗口（auth.go:235-243）——9 次/5 分钟可无限续期（≈108 次/小时爆破面）；与蓝图 A5"滚动窗口"措辞漂移
28. TrustProxy=1 取 XFF 首地址（追加型反代下客户端可控）→ 限速绕过 + fails map 无硬上限（server.go:116-131、auth.go:247-254）——规格层弱点+清理不完备叠加
29. 会话 cookie 缺 Secure 属性（auth.go:128-137；冒烟输出实证）——TLS 反代形态下明文回源携带；直接加会破坏纯 HTTP 形态，需按部署开关
30. maskedKeys 对短 key（9-12 字符）泄露 8/N 字符（security.go:199-205）
31. SetProxyKey 内存缓存不过滤空串项，与 ValidKeys 行为不一致（security.go:136-141 vs 98-104）——不可利用
32. 首请求遇 stat 抖动且缓存为空 → 免密 fail-open 窄口（security.go:87+61-62）
33. SetProxyKey 不校验 key 内容：内嵌换行/控制字符入库 → /v1 永久 401（security.go:115-128）

**M12/M13（WebUI/部署）**
34. 前端备注名预规范化缺 64 上限与 index 保留字（index.html:415-418）——后端 Slugify 返回空走 AutoName，别名无声丢失（9ddb1f8 F7 的残留缺口）
35. /healthz 免登录返回账号元数据 userId/teamId/teamName（server.go:189-198）——超出监控需要；且 :194 每次 healthz 读盘
36. atomicfile rename 失败分支不清理 tmp（atomicfile.go:43，与 :19 注释矛盾）+ 无启动清扫——凭据明文 .tmp 可残留
37. /api/balancer/config 类型脏值静默吞恒 200（server.go:286-296）——调用方无从分辨未生效
38. env 管理密钥时 WebUI 保存静默 no-op 仍报成功（security.go:115-143 vs 87-97）——文件写了但永不生效
